# 013.2 — Secure update staging
Use a trusted external copy of secure_update.py and release_signature.py, with cryptography installed. Keep the owner public key independently pinned. Run `python secure_update.py archive.zip trusted-public.bin archive.sig 013.1 NEW_EMPTY_PATH`. The version argument must be obtained from trusted deployment records, not the incoming archive. The tool stages only; it does not run code or alter the active project. Stop services, back up SQLite and D1, check migration compatibility and test the staged release before manually switching. Retain the old code and compatible database snapshot; do not blindly roll back database migrations. No automatic activation or rollback. The previous release used an ephemeral signing key; establish an owner key for future releases. The new archive is unsigned until signed with that key. Use a private staging parent directory; a local attacker with write access to that directory is outside this tool's protection. Limits: 5000 entries, 256 MiB uncompressed.
