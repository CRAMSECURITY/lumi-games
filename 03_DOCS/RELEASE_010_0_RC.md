# LUMI 010.0 RC — кандидат, не production-ready
База 009.4 DATABASE VAULT. Изменения объединены в одном архиве; дизайн и ресурсы сохранены. 

## 009.5 Global Ban
SQLite-триггеры записывают изменения блокировок в транзакционную очередь. Основной бот отправляет подписанные события по HTTPS, без причин блокировок и ID модераторов. Worker проверяет подпись, время и порядок событий для каждого ID, проверяет блокировку при авторизации и каждом запросе. Повторные и устаревшие события не меняют более новое состояние. Профильные ограничения не являются блокировками аккаунтов. Очередь повторяется примерно через 10 секунд после завершения прохода; при сетевом сбое блокировка Mini App задерживается. Это не синхронная распределенная транзакция. Без настроенного ключа доставка не работает; проверять очередь обязательно. При восстановлении старой SQLite последовательность событий может отстать от D1: перед повторным запуском требуется ручная сверка D1 и счетчика очереди; не очищать таблицу D1 без сверки. Записи последнего состояния остаются в D1 для защиты от повторов, политика хранения требует отдельной разработки.

## 009.6 Performance
Обработчики наклона карточек больше не отменяют уже запланированный кадр при каждом движении указателя, а используют последнее положение. Визуальный эффект прежний. Реальные FPS, задержки загрузки и размер GLB не измерены/не изменены.

## 009.7 Recovery
`python 01_BOT/lumi_restore.py PATH_TO_BACKUP PATH_TO_NEW_DB` — проверка Fernet и SQLite integrity_check, публикация в новый файл без перезаписи. Ключ в переменной LUMI_BACKUP_KEY. Требуется файловая система с поддержкой жестких ссылок. Проверено локально; восстановление действующего сервера и D1 не проверено. Перед ручной заменой остановить оба бота, сохранить действующую базу и WAL, сверить состояние блокировок D1.

## 009.8 Monitoring
`python 04_TOOLS/check_runtime.py PATH_TO_DB --url HTTPS_MINI_APP_URL` — проверка SQLite, длины очереди блокировок, ответа health и времени запроса. Код выхода 0 только при здоровых проверках и пустой очереди; 1 при проблеме, 2 при ошибке проверки. Worker health сообщает наличие ключа без его значения. Это инструмент проверки, а не развернутый постоянный мониторинг. Настроить внешнее расписание и уведомления отдельно.

## 009.9 / 010.0 RC — проверка
36 JS тестов, 21 выбранный Python offline тест, синтаксис 40 Python и 29 JS файлов. Полный runtime aiogram не проверен: библиотека отсутствует. Нагрузочный тест реальной системы, актуальный аудит зависимостей, независимый пентест, реальный Telegram, платежи, WebGL Android/iOS, проверка совершеннолетия, шифрование рабочей БД и гарантированное удаление данных остаются обязательными до публичного запуска. Не считать все уязвимости закрытыми.

## Развертывание только в тестовой среде
1. Сохранить исходную версию, .env, SQLite и резервную копию D1. Проверить восстановление.
2. Применить миграции D1 до 0004_global_ban.sql включительно. Убедиться, что используется отдельная тестовая D1, не рабочая.
3. Создать новый случайный секрет (например `python -c "import secrets; print(secrets.token_hex(32))"`). Сохранить одинаковое значение в .env бота `LUMI_BAN_SYNC_KEY` и секрете Worker (`npx wrangler secret put LUMI_BAN_SYNC_KEY` в тестовом окружении). Не включать в архив. Использовать отдельный LUMI_BACKUP_KEY. 
4. Обновить Worker и оба бота совместно. Запустить основной бот, затем админ-бот. Проверить очередь и health. Проверить блокировку и разблокировку тестового пользователя, в том числе с уже активной сессией; имитировать сетевой сбой и восстановление связи. 
5. Не публиковать до завершения перечисленных выше проверок. Существующие настройки Cloudflare в архиве указывают на прежний проект; перед любым deploy проверить конфигурацию.
